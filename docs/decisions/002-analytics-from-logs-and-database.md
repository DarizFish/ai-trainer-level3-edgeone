# 002 · 以业务日志与数据库承担数据分析

状态：已决定，第一批记录点和可重复运行的汇总已实现；线上验证状态见 [`../STATUS.md`](../STATUS.md)。决定日期：2026-09-26。第一阶段的指标与事件口径见 [`../ANALYTICS.md`](../ANALYTICS.md)。

## 要解决的问题

网站需要同时回答三类问题：用户在浏览器里经历了什么、服务端业务动作是否成功、账号当前保存了什么学习结果。
HTTP 请求只能证明某个地址被访问，不能证明答题写入、交卷或浏览器内实验就绪。
另一方面，按题覆盖更新的进度表保存的是当前状态，不能还原每次操作的历史。

## 考虑过的方案

| 方案 | 取舍 |
| --- | --- |
| 只分析 CDN／Nginx 访问日志 | 可分析请求与故障，但静态资源、重复请求和机器人会混入计数；无法可靠判断业务成功 |
| 接入独立埋点服务 | 可以提供现成的事件与漏斗能力，但增加一个数据接收方、运行依赖和维护面 |
| 在网站内统一记录服务端业务事件和必要的浏览器事件，结合数据库汇总 | 能覆盖浏览器与服务端各自可观察的结果；数据库继续承担学习状态的事实来源；需要自行定义事件和指标口径 |

## 决定

采用第三种方案。服务端动作在业务成功或失败的边界产生日志；浏览器独有的体验信号经本站同源接口上报，由网站写入相同的结构化日志流。账号、进度与成绩等业务事实从数据库读取。
不增加独立部署的埋点服务，不让浏览器直连日志厂商，也不把日志作为成绩或学习记录的恢复来源。浏览器事件是尽力上报的观察数据，不能冒充服务端已提交的业务事实；日志写入或采集失败不能改变业务请求或页面操作结果。

应用只依赖仓库定义的事件协议，并向标准输出写一行 JSON。采集、存储、查询后端由部署层接入，可替换；厂商 SDK、专有字段与查询语法不能成为应用事件协议或指标定义的唯一实现。汇总规则与事件版本留在仓库，切换日志服务时仍可从通用日志格式重建报表。

第一阶段不在新增业务事件中写邮箱、IP、会话令牌、密码、原始答案或草稿，也不写可跨请求追踪个人的标识。
因此日志中的“次数”不是“人数”；跨请求的独立学员数和完整转化漏斗不属于这一阶段的可计算指标。浏览器事件可以统计环境就绪或失败的上报次数，不能据此声称代码运行成功或考试完成。
若未来确需这些指标，应先确定必要性、关联标识、保留期限、删除方式和用户告知，再扩展事件协议。

## 重新考虑的条件

当产品明确需要跨设备学员漏斗、真实代码运行完成率或长期用户留存分析时，重新评估事件标识与成功判据。日志后端的成本或能力变化时可替换采集与查询适配，不改变应用事件协议；不把这些需求暗中塞入访问日志。
