# 单机双槽容器发布，切流独立确认

状态：已决定并写入发布代码；生产预备与切流尚未验证。

## 问题

原 systemd 和第一版容器脚本都要先停旧实例、再占用 3000 端口启动新版。这个顺序制造服务空窗；失败回退还要重新启动旧进程。Nginx 同时从 `current` 读取静态文件，单独切换代理端口会让页面与资源短暂来自不同版本。

## 考虑过的方案

- **同端口替换**：变更最少，但新实例健康之前旧实例必须退出。
- **同机双槽**：3000/3001 同时运行，先验证候选，再由 Nginx 切流；仍受单机故障影响。
- **多机加负载均衡**：可覆盖主机故障，但对当前个人站增加服务器、网络和运维成本。

## 决定

采用同机 blue/green 两槽。受限部署命令只验包、执行一次性迁移、启动空闲端口的候选容器并验证 readiness；它不得修改现用 Nginx 配置或停止旧实例。最终切流由 root-only 命令在人工确认后执行。Nginx 的代理端口、静态目录和可信回源配置由同一份版本化配置确定，graceful reload 后旧 worker 继续处理已有请求。旧实例保留到观察期结束，供即时回退。

旧页面可能继续请求旧静态文件。预备阶段以新版为主建立版本化静态目录，补入旧版缺失的文件；同一不可变 URL 若对应不同字节，拒绝预备。数据库迁移使用同一镜像的一次性容器并保留 advisory lock；Web 容器不接收 `DIRECT_URL`。迁移只按 expand/contract 推进，回退应用不反向迁移数据库。

## 假设与重新评估条件

- 单机资源可暂时容纳两个 Web 进程和版本化静态文件；上线前需实测内存、磁盘与候选负载。
- 源站主机故障不在此次发布切换目标内；若需要机器级可用性，再评估第二主机与外部负载均衡。
- 若版本化静态目录增长超过可接受空间，应引入明确的保留与清理策略或对象存储；不得在旧页面可能仍引用资源时直接删除。
- 若 Nginx 语法、候选 readiness、旧版兼容性或回退路径在预备阶段不能验证，停止在切流前。
